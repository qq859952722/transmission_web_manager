# Transmission WebUI 项目全面审计提示词（Google Antigravity 专用）

## 审计任务总览
你现在是一位资深的前端工程师和Transmission协议专家，需要对一个刚完成从jQuery到Alpine.js迁移的Transmission WebUI项目进行**全面、深入、可验证**的代码审计。**绝对禁止直接修改任何代码**，所有发现必须通过实际测试验证后，生成结构化的Markdown审计报告。

## 前置准备与验证环境要求
1. **官方文档深度研读**：完整阅读Transmission官方最新RPC协议文档（https://github.com/transmission/transmission/blob/main/docs/rpc-spec.md），包括所有RPC 2.0方法、字段、参数、返回值、错误码，以及历史版本变更记录
2. **本地服务验证**：连接本地运行的Transmission服务（默认地址：http://127.0.0.1:9091/transmission/rpc），使用实际的RPC调用验证所有前端实现
3. **配置文件分析**：读取并解析Transmission的settings.json配置文件，对比前端暴露的所有配置项
4. **自动化测试工具**：使用Chrome Headless和Node.js编写临时测试脚本，验证所有交互流程和API调用
5. **协议兼容性验证**：同时测试RPC 2.0协议和旧版本协议的兼容性，验证rpc-legacy-adapter的实现

## 核心审计维度

### 一、RPC协议实现完整性与正确性审计（最高优先级）
1. **RPC 2.0协议主逻辑检查**
   - 验证项目是否严格遵循"主逻辑基于RPC 2.0，通过rpc-legacy-adapter兼容旧版本"的架构设计
   - 检查所有核心功能是否优先使用RPC 2.0方法和字段
   - 验证rpc-legacy-adapter的转换逻辑是否正确，是否存在字段映射错误

2. **接口全覆盖验证**
   - 列出Transmission官方RPC规范中所有方法，逐一标记前端是否已实现
   - 对每个已实现的方法，验证：
     - 请求参数是否完整且正确
     - 返回值处理是否覆盖所有字段
     - 错误处理是否符合官方规范
     - 批量操作是否正确实现
   - 对未实现的方法，**特殊标注**并分析：
     - 该方法的功能和使用场景
     - 实现的价值和优先级
     - 推荐的实现方法和注意事项

3. **配置项完整性审计**
   - 对比settings.json中的所有配置字段与前端可修改的配置项
   - 检查是否存在前端未暴露但用户常用的配置
   - 验证每个配置项的读写逻辑是否正确
   - 检查配置项的类型转换和边界值处理

4. **协议兼容性测试**
   - 测试在不同Transmission版本（3.0.x, 4.0.x, 4.1.x）下的兼容性
   - 验证旧版本特有的字段和方法是否通过adapter正确处理
   - 检查是否存在硬编码的版本判断逻辑

### 二、jQuery到Alpine.js迁移质量审计
1. **迁移完整性检查**
   - 全局搜索项目中所有jQuery代码（$符号、jQuery关键字）
   - 列出所有未完成迁移的jQuery代码片段及其位置
   - 评估这些代码迁移到Alpine.js的难度和必要性

2. **迁移正确性验证**
   - 检查DOM操作是否正确转换为Alpine.js的响应式模式
   - 验证事件绑定是否正确，是否存在事件泄漏
   - 检查数据绑定是否正确，是否存在数据不同步问题
   - 验证动画和过渡效果是否正常工作
   - 检查表单处理和验证逻辑

3. **迁移引入的问题检测**
   - 查找因迁移导致的功能失效
   - 检查是否存在Alpine.js特有的错误（如x-data作用域问题、x-for键值问题）
   - 验证第三方库与Alpine.js的集成是否正确

### 三、代码质量与缺陷审计
1. **Bug与逻辑缺陷检测**
   - 全面扫描代码中的潜在bug：
     - 空指针异常和未定义变量
     - 异步操作竞态条件
     - 错误处理缺失或不完整
     - 边界条件处理错误
     - 类型转换错误
   - 对每个发现的问题，**必须通过本地测试复现**，并提供复现步骤

2. **死代码与冗余代码清理**
   - 识别并列出所有未使用的变量、函数、组件和文件
   - 检查是否存在重复的代码片段
   - 查找已注释掉的代码块
   - 评估这些代码是否可以安全删除

3. **代码结构与可维护性**
   - 检查代码组织是否合理
   - 评估函数和组件的单一职责原则遵守情况
   - 检查是否存在过大的函数或组件
   - 验证命名规范的一致性

### 四、性能审计与优化建议
1. **前端性能检测**
   - 使用Chrome DevTools分析页面加载性能
   - 检查首次内容绘制(FCP)和最大内容绘制(LCP)
   - 评估JavaScript执行时间和主线程阻塞情况
   - 分析DOM节点数量和复杂度

2. **RPC调用性能优化**
   - 检查是否存在不必要的频繁RPC调用
   - 验证批量操作的使用是否合理
   - 评估数据缓存策略的有效性
   - 检查长轮询或WebSocket连接的实现

3. **渲染性能优化**
   - 检查列表渲染性能（特别是种子数量较多时）
   - 验证是否存在不必要的DOM重绘和重排
   - 评估Alpine.js响应式更新的效率
   - 提供针对性的性能优化建议

### 五、用户体验与人性化功能审计
1. **现有交互体验评估**
   - 检查常见操作的流程是否流畅
   - 评估错误提示和状态反馈的清晰度
   - 验证响应式设计在不同屏幕尺寸下的表现
   - 检查键盘导航和无障碍访问支持

2. **人性化功能提升建议**
   - 基于Transmission的功能特性，提出可提升用户体验的新功能点
   - 分析这些功能的实现难度和用户价值
   - 提供功能设计的初步思路

## 审计报告输出要求
1. **报告格式**：严格使用Markdown格式，结构清晰，层次分明
2. **报告结构**：
   - 审计概述（审计范围、环境、时间）
   - 总体评分和结论
   - 各审计维度的详细报告
   - 问题分级（严重、重要、一般、建议）
   - 未实现RPC接口和配置项清单
   - 优先级排序的改进建议
   - 后续行动计划

3. **问题描述要求**：
   - 每个问题必须包含：问题描述、文件位置、复现步骤、影响范围、修复建议
   - 所有问题必须经过本地测试验证，无法复现的问题不得列入报告
   - 提供相关的代码片段和截图说明

4. **绝对禁止**：
   - 直接修改任何代码
   - 提供未经测试的修复方案
   - 主观臆断的问题描述
   - 模糊不清的建议

## 执行原则
1. **验证优先**：所有发现必须通过实际的RPC调用和浏览器测试验证
2. **客观准确**：基于事实和代码进行分析，避免主观猜测
3. **全面深入**：覆盖所有代码文件和功能模块
4. **可操作性**：所有建议必须具体、可执行
5. **优先级明确**：区分问题的严重程度和紧急程度
